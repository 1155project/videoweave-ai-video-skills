# AI Consumer Integration — Integration Points

## Overview

VideoWeave will expose a hosted MCP (Model Context Protocol) server that allows AI agents
to interact with the platform on behalf of authenticated users. Users configure their LLM
client (Claude Desktop, custom agents, etc.) to connect to the VideoWeave MCP endpoint
using a personal API key. The agent can then manage projects, upload files, and execute
video editing operations using a set of provided skills.

---

## Why MCP

MCP is the right choice over alternatives:

| Approach | Pros | Cons |
|---|---|---|
| **MCP (chosen)** | Provider-agnostic, standard protocol, portable skill packages | Requires users to configure MCP client |
| Raw OpenAPI + function calling | Zero new infra, existing API works | Requires per-provider setup, no portable skill packages, no standard auth flow |
| GraphQL | Flexible queries | Extra infra, no AI-native adoption |
| Custom agent SDK | Maximum control | Single LLM vendor lock-in |

MCP is the only approach that supports the skill package distribution model (write once,
translate to other formats later) and works across Claude, OpenAI agents, Gemini, and
any MCP-compliant client.

---

## Architecture

### Deployment

The MCP server is implemented as a new module within the existing FastAPI backend — not a
separate service. This avoids duplicating auth middleware, database connections, RabbitMQ
clients, and MinIO integrations.

```
Existing backend:
  /api/v1/...          ← existing REST API (unchanged)
  /mcp/v1/...          ← new MCP server module

New module structure:
  backend/src/
    mcp/
      __init__.py
      server.py           ← MCP protocol handler (JSON-RPC over HTTP/SSE)
      auth.py             ← API key validation + session token management
      tools/
        account.py        ← get_account_info
        projects.py       ← list/create/get/update/delete project tools
        files.py          ← list/upload/download/delete file tools
        track.py          ← track management tools
        edit.py           ← all async edit operation tools
        jobs.py           ← job status tools
      models.py           ← McpApiKey DB model
      schemas.py          ← MCP tool input/output schemas
```

### MCP Protocol

MCP uses JSON-RPC 2.0. The server exposes:
- `initialize` — announces server capabilities and tool list
- `tools/list` — returns available tools with schemas
- `tools/call` — executes a tool call

Transport: HTTP with Server-Sent Events (SSE) for streaming responses. Standard MCP spec.

**Endpoint:** `https://vs_api.1155project.com/mcp/v1`

## Authentication

### Two-Layer Auth

**Layer 1 — API Key (long-lived)**
- User generates in VideoWeave account settings
- Stored as a SHA-256 hash in `mcp_api_keys` table (never stored in plaintext)
- Scoped to the user's tenant
- Can be revoked from account settings

**Layer 2 — Session Token (short-lived)**
- Generated by the MCP server at MCP `initialize` handshake time
- Short-lived JWT with `mcp_session` claim (8-hour expiry)
- All subsequent tool calls use the session token
- Never visible to the user or the LLM
- Silent refresh: when a session token reaches 80% of its TTL, the server issues a new
  one transparently. The API key is held server-side in memory during the session for
  refresh purposes.

### New Database Table

```sql
CREATE TABLE mcp_api_keys (
    id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id     UUID NOT NULL REFERENCES users(id),
    tenant_id   UUID NOT NULL REFERENCES tenants(id),
    key_hash    VARCHAR(64) NOT NULL UNIQUE,  -- SHA-256 of raw key
    name        VARCHAR(100) NOT NULL,        -- user-defined label ("My Claude Key")
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    last_used_at TIMESTAMPTZ,
    is_active   BOOLEAN NOT NULL DEFAULT true
);
```

### Auth Flow

```
1. User generates API key in VideoWeave → receives raw key once (never shown again)
2. User adds key to LLM client config (e.g., Claude Desktop mcp_servers entry)
3. LLM client connects: POST /mcp/v1/initialize { "api_key": "vw_..." }
4. MCP server validates key (hash lookup), creates session token, returns capabilities
5. LLM stores session token in memory for this session
6. All tool calls: { "session_token": "...", "tool": "...", "params": {...} }
7. Server middleware checks token age → if >80% TTL, silently issues new session token
   in response header (X-MCP-Session-Refresh: <new_token>)
8. Session ends on disconnect or token expiry without activity
```

### API Key Generation Endpoints (new REST endpoints in auth module)

```
POST   /api/v1/mcp-keys              — create new API key (returns raw key once)
GET    /api/v1/mcp-keys              — list user's API keys (names + created dates only)
DELETE /api/v1/mcp-keys/{key_id}     — revoke a key
```

## File Transfer Patterns

### Reads (images, thumbnails, video previews)

MCP tools return presigned MinIO URLs directly. The agent can reference the URL without
authentication headers. URL TTL: 1 hour (existing behavior from `get_presigned_url` endpoint).

### Uploads (local files → VideoWeave)

The MCP server cannot access the user's local filesystem. Uploads use a two-step pattern:

**Step 1 — Agent calls `prepare_upload` MCP tool:**
```json
{
  "tool": "prepare_upload",
  "params": {
    "project_id": "uuid",
    "filename": "clip01.mp4",
    "file_type": "WORKING"
  }
}
```
Response:
```json
{
  "upload_url": "https://minio.../presigned-upload-url",
  "file_id": "uuid",
  "expires_in": 3600
}
```

**Step 2 — Agent calls local `videoweave-upload` CLI script:**
```bash
videoweave-upload --url "<upload_url>" --file "./clips/clip01.mp4"
```

The CLI script is provided by VideoWeave as a downloadable helper. It handles:
- Streaming the file bytes to the presigned URL (MinIO PUT request)
- Progress reporting
- Retry on network errors

After the upload completes, the `file_id` is already registered in the database by the
`prepare_upload` tool — no second confirmation call needed.

**Dependency note:** The upload flow requires the agent to have a mechanism for executing
local scripts (e.g., bash tool in Claude Desktop, computer-use, or similar). This should
be documented in the MCP server's user setup guide.

### Downloads (VideoWeave → local files)

`get_file_url` returns a presigned download URL. The agent can:
1. Provide the URL to the user for manual download
2. Call a local `videoweave-download` CLI script to save to a local path

## Async Operation Pattern

All edit operations (cut, join, slow, speed up, add audio, remove audio, add logo, add
text, finalize) are asynchronous. They return `HTTP 202 Accepted` with a job object:

```json
{
  "job_id": "uuid",
  "status": "QUEUED",
  "operation": "CUT",
  "created_at": "2026-06-26T..."
}
```

The agent MUST poll `get_job_status` until status is `COMPLETED` or `FAILED`.

**Recommended polling interval:** 3 seconds (matches typical job processing time).

The skill documents for each edit operation include explicit polling instructions so the
agent handles this correctly without user intervention.

## Skill System Design

### Two-Tier Structure

**Tier 1 — Atomic Skills** (one MCP tool call each)
One markdown file per operation. Located in `skills/atomic/`. Self-contained: includes
inputs, the exact MCP tool call, expected output, and chaining metadata.

**Tier 2 — Chain Skills** (sequences of atomic skills)
Located in `skills/chains/`. Reference atomic skills by name. Include the full step
sequence, decision points, and error recovery. Can be user-authored or VideoWeave-provided.

### Skill Manifest

`skills/atomic/00_skill_manifest.md` is a single routing document loaded by the agent
at session start. It contains:
- Full catalog of available skills with one-line descriptions
- Dependency graph (which skills require others to run first)
- Common multi-step pattern examples (implicit chain hints)
- Output/input compatibility matrix for chaining

The manifest is the agent's "table of contents" — it reads this first, then pulls
individual skill files as needed.

### Skill Package Distribution

A skill package is a zip/tarball of all skill markdown files, installed into the user's
LLM client as a set of custom instructions or context files. Initial package targets
Claude (CLAUDE.md skills format). Future translation targets:

| LLM Platform | Format |
|---|---|
| Claude | CLAUDE.md skill files (current) |
| OpenAI GPT Actions | OpenAPI spec + system prompt |
| OpenAI Assistants API | Function definitions JSON |
| Generic | System prompt injection |

Translation is mechanical once atomic skills are tested and stable. The logic does not
change — only the format wrapper.

### Future: Skill Repository

A public repository (hosted by VideoWeave or on GitHub) where users can publish and
download complex chain skills. Examples: "Create LMS-compatible video", "Brand all
clips with intro/outro/logo", "Split long recording into chapters". Discovery via a
future `/skill-library` page in the VideoWeave UI.

## Scenario 2 — In-App Chat (Planning Summary)

> Full design to be developed when Scenario 1 is complete and battle-tested.

### Vision

An AI chat panel embedded in the VideoWeave editor UI. The user describes an action
("cut this clip at 2:30") and the AI executes it directly against the current project
state — no MCP client setup required.

### Key Architectural Differences from Scenario 1

| Concern | Scenario 1 (MCP) | Scenario 2 (In-App Chat) |
|---|---|---|
| LLM provider | User's own (Claude Desktop, etc.) | VideoWeave-hosted (Anthropic API backend call) |
| Auth | User's API key → MCP session | Existing VideoWeave JWT session |
| Context delivery | Skill files loaded by user's client | Backend injects current project state per message |
| File access | CLI upload helper | Direct server-side access |
| Action execution | MCP tool calls | Direct service calls from chat handler |

### Components Needed

1. **Chat UI component** — collapsible panel in editor, message history, action confirmation dialogs
2. **Chat backend service** (`backend/src/services/chat_service.py`) — manages conversation history, context injection, LLM calls
3. **LLM API integration** — Anthropic SDK (Claude), server-side. API key in backend `.env`, never exposed to client
4. **Context manager** — assembles current project state (track clips, files list, job status) as context for each LLM request
5. **Action execution bridge** — chat service calls existing track/file services directly after LLM determines the action
6. **Conversation history storage** — PostgreSQL table or MongoDB (existing). TTL-based cleanup.
7. **Action confirmation flow** — destructive operations (delete, overwrite) surface a confirmation UI before execution

### Key Decisions Deferred

- LLM model selection and cost model (per-message cost passed to user vs. included in plan)
- Conversation history retention policy
- Scope of autonomous actions vs. confirmation-required actions
- Whether chat service reuses MCP skill definitions or has its own prompt library

### Reuse from Scenario 1

The action execution layer (calling track_service, files_service, etc.) is identical.
Scenario 1's skill definitions can serve as the prompt library for Scenario 2 with
minimal adaptation — the inputs/outputs are the same, only the delivery mechanism changes.

## Implementation Phases (Scenario 1)

### Phase 1 — Foundation
- `mcp_api_keys` table and migration
- API key CRUD endpoints in auth module
- Account settings UI: "Developer" section for API key management
- MCP server module scaffold (FastAPI router + JSON-RPC handler)
- Auth middleware (API key → session token)

### Phase 2 — Read Tools
- `get_account_info`, `list_projects`, `get_project`, `list_files`, `get_track`, `get_job_status`
- End-to-end test: configure Claude Desktop, list projects

### Phase 3 — Write + Edit Tools
- All project CRUD tools
- File upload (prepare_upload + CLI helper)
- All edit operation tools with job polling
- Undo

### Phase 4 — Skills Package
- Write and test all atomic skill files
- Write and test skill manifest
- Write example chain skills
- Package as installable zip

### Phase 5 — Hardening
- Rate limiting per API key
- Audit log (which key called which tool, when)
- Key rotation reminder (flag keys >90 days old)
- Token usage tracking for MCP sessions

## Open Questions for Implementation

1. **MCP transport:** SSE vs WebSocket? SSE is simpler and sufficient for the initial
   implementation. WebSocket provides true bidirectional streaming if needed later.

2. **Presigned upload URL generation:** The `prepare_upload` tool needs a MinIO presigned
   PUT URL. The existing `minio_service` supports this — verify the PUT URL works for
   direct client uploads without triggering the existing upload validation logic (file type
   check, size check, codec validation). These checks may need to run post-upload instead.

3. **Rate limiting:** Per-API-key rate limits should be independent of the existing
   per-IP limits in the REST API. Design the MCP middleware to apply its own limits.

4. **Credit consumption:** MCP-triggered edit jobs consume credits the same as UI-triggered
   jobs — no changes needed to `tracks_service._check_and_reserve_credits()`.
